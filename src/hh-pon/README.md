# hh-pon: open GPON ONU stack for the HH4000 (BCM6858)

A skeleton for an open replacement of the Broadcom PON stack (`bcm_pondrv` + `gponstack` + `bcmgpon` +
`omcid`). The design is in `docs/15-open-pon-design.md`. The
hardware facts come from docs 08 and 11–14.

| Path | What | State |
|---|---|---|
| `core/hh_ploam.[ch]` | G.984.3 PLOAM codec (DS decode, US encode, CRC-8) | complete for GPON, host-tested |
| `core/hh_gpon_fsm.[ch]` | O1..O7 activation state machine behind an ops vtable | complete for GPON, host-tested, follows stock timing (TO1 = 20 s over O3+O4) |
| `core/hh_gpon_calc.h` | TDLY/EqD encoding, random delay, RPLM image, overhead check | host-tested against the stock emulation values |
| `tests/test_main.c` | host unit tests (`make test`, ASan + UBSan) | 116 checks |
| `kmod/hh_pon_main.c` | platform driver: WAN SerDes init, GPON MAC init, ops → registers, IRQs, timers, debugfs | **skeleton**: compiles for arm64 against Linux 6.18; untested on hardware; `TODO`/`[U]` marks the gaps |
| `kmod/gen/hh_pon_replay.h` | generated replay tables (110 SerDes + 514 MAC steps) | generated by `make kmod` from `work/pon/gpon/replay/replay_init.txt` |
| `include/xrdp-pon.h` | MAC ⇄ Runner contract (docs/14 §10) | proposal; no Runner driver implements it yet |
| `include/hh_omci_backend.h` | southbound interface for an open omcid (stock-ABI and native backends) | proposal |
| `dt/brcm,bcm6858-gpon.yaml` | DT binding draft | draft |
| `tools/replay2c.awk` | replay text → C table generator | |

```sh
make test                 # host unit tests
make kmod                 # arm64 module against ../../ref/linux/linux-6.18.60 (prepared tree)
```

## Safety

- **The laser stays off unless the module is loaded with `tx_enable=1`.** With `tx_enable=0` the
  driver is receive-only: SerDes, downstream sync, and PLOAM sniffing once the Runner is attached.
- An ONU that transmits outside its grants disturbs every subscriber on the same splitter. Do the
  first transmit tests against a lab OLT, not an ISP's PON (docs/15 §6).
- The serial number and password are opaque configuration inputs (module parameters). Don't commit
  real values.
