# 10G cable insertion restart investigation

The user reported an immediate restart when plugging into the 10G copper WAN after booting without the cable. The first observed boot had only a few minutes of uptime. The vendor watchdog module described its cause as unknown, while the kernel boot log reported `Last RESET due to SW reset`, reason `0x80000000`. No prior panic trace was retained and `/sys/fs/pstore` is absent. Kernel settings are panic=3 seconds and panic_on_oops=1, so a panic can produce a quick software reset. These observations do not identify the caller or establish a driver fault.

The router subsequently operated with eth4 negotiated at 2.5 Gb/s. With continuous UART recording, the user unplugged/replugged once and it stayed running. The user then suggested reproducing the original boot sequence. Logs were saved, the filesystem was synced, and the router was deliberately cold-cycled using the verified D12 relay while eth4 was unplugged. This controlled cold boot reported POR reset, reason `0x00000000`, unlike the original incident's SW-reset report.

After the uncabled cold boot reached normal SSH/panel/AP operation, a baseline boot identifier and link-down state were recorded. The user inserted the 10G cable once. eth4 came up at 2.5 Gb/s, WAN DHCP recovered and the boot identifier remained unchanged. Four further samples across a 90-second observation also retained the same boot identifier and link. The continuous cold-boot/first-link UART trace contains no kernel panic, internal-error stack trace or physical RESET reboot marker. No claim is made that the original fault is fixed: it was not reproduced.

Final checks: WAN ping succeeded, all three APs reported ENABLED, the Python panel was ready, RESET was released/armed, and MTD3/MTD4 ECC-failure counters were zero. SSH recovered after an initial banner-exchange failure. Nothing in the present evidence establishes the Ethernet driver, the Arduino hat or a particular service as the cause. The different SW/POR reports make a software-triggered reset more likely than a complete loss of router input power, with the usual limits of reset-cause reporting.

No intentional firmware or configuration writes were made for this investigation. One user-requested cold power cycle was performed after syncing. Normal boot/services may update their own persistent state. No speculative source fix or acceleration change was installed. Diagnostic commands and a temporary Windows capture helper were created under the existing hh-panel-audit directory. Project artifacts are `work/eth4-crash/` (pre-boot/current logs, UART recordings, boot-ID samples, helper copy and result.json) and this document. The helper copy is an experiment record for the Windows harness, not a portable installation tool. All temporary capture/monitor processes have ended.

If the event recurs, record UART before boot and through insertion. Preserve the final lines before the new boot: an oops/panic stack, HH_RESET_SHORT_PRESS_REBOOT marker or orderly reboot message would distinguish the leading software paths. Wall-clock log times jump when WAN NTP becomes available; use monotonic uptime and boot identifiers to establish restarts.

## Remaining readiness work

1. Investigate any recurrence of unexplained resets and assess sustained household stability before treating this as a dependable main router. This incident and the earlier unexplained RAM-test restart remain unresolved observations.
2. Validate sustained routed throughput/latency and acceleration under actual clients and mixed wired/Wi-Fi traffic. Full 10 Gb/s routing has not been measured; the current upstream link is 2.5 Gb/s. The phone already demonstrated substantially improved 5 GHz throughput after the 80 MHz change.
3. Validate the features actually needed in the intended network: guest isolation/VLANs, PPPoE if applicable, and VPN/SQM interactions with hardware offload. IPv6 public LAN access still requires upstream prefix delegation or another deliberate routing design.
4. Add a board-specific firmware upgrade workflow that preserves the separate data volume. The current verified approach boots RAM and updates selected system volumes; generic sysupgrade remains unsupported.

PON remains optional/deferred. The retained vendor kernel/BSP remain a maintenance/security limitation; the user deferred a modern-kernel/nftables port. Panel configuration/Python modes, buttons/LEDs, configurable RESET, Wi-Fi 80 MHz support, Ethernet WAN, IPv4 firewall/hardware NAT and SSH key access are already implemented, with validation limits described in their respective documents.

## Follow-up: dying-gasp evidence

Later multi-port validation captured repeated `D%G` markers immediately before resets even after the RAM-only test configuration disappeared. Disassembly of the backed-up stock `kerSysDyingGaspIsr` at 0xffffffc0004651f0 confirms direct UART writes of 0x44, 0x25 and 0x47, followed by wireless power-down, callback dispatch, watchdog start and an infinite wait. Therefore the earlier SW-reset report does not distinguish a software bug from a power-loss detection event: this handler itself arranges a watchdog reset. The signal may indicate actual voltage loss or a false power-loss interrupt; the specific cause is not yet established. A relay-bypass test was requested. No new VPN/SQM modules had been loaded. See the ongoing validation notes for results.
